1. 项目概述

1.1 背景与痛点

使用者是一家一人经营的代理记账公司（老板 = 唯一操作者 = 会计 = 管理员），同时为约 100 家中小微企业提供代理记账与报税服务。当前工作方式的痛点：

#痛点具体表现
P1客户与期限管理散乱100 家客户的资料、合同到期日、各税种申报期限分散在 Excel、微信、脑子里，容易漏报、漏收
P2凭证手工录入效率低每月数千张发票、银行流水靠手工录凭证，重复劳动占比极高
P3多客户切换繁琐每换一家客户就要切换一套账，缺少统一总览与批量处理视角
P4外贸客户流程特殊需对接单一窗口、电子口岸、外汇等平台，报关/收汇/退税资料容易断档
P5数据安全无保障客户账务数据在单机 Excel/旧软件中，无自动备份，硬盘故障即灾难
P6专业软件重且贵主流代账软件按客户数收费、年费高，且很多功能为多人团队设计，单人用不动

1.2 项目目标

  • G1 统一工作台：一个浏览器界面管完 100 家客户的档案、合同、记账、报税、收费、文档。
  • G2 自动记账：发票、银行流水按规则自动生成凭证（借鉴 Odoo 的 account.reconcile 自动对账模型思想），把手工录入量降到 20% 以下。
  • G3 不漏不迟：申报日历 + 任务看板，每客户每税种每属期的申报状态一目了然。
  • G4 外贸专区：报关单、出口发票、收汇结汇、出口退税全流程台账。
  • G5 本机部署 + 云备份：系统跑在自己电脑上（无外网依赖、数据不出本机），SQLite 单文件数据库每日自动备份到 OneDrive 同步目录。
  • G6 Odoo 级的架构品质：模块化、模型驱动 UI（Metadata-driven UI）、多账套隔离、操作审计——把 Odoo 二十年沉淀的 ERP 架构精华移植到轻量技术栈上。

1.3 范围界定（Scope）

做（In Scope）：

  • 单机 Web 应用（本机浏览器访问 localhost），单用户为主、预留多角色。
  • 100 家客户账套的数据隔离与全局总览。
  • 借鉴 Odoo 架构的自研系统（详见第 3 章"借鉴策略"）。

不做（Out of Scope，第一版明确排除）：

  • 不直接对接税局/海关的 API 自动申报（政策与安全原因，系统只做计算底稿 + 状态台账 + 官网快捷入口，实际申报由用户在电子税务局/单一窗口人工完成，完成后回系统登记状态）。
  • 不做多用户实时协同、不做移动 App（Web 响应式布局可被手机浏览器访问即可）。
  • 不做进销存、生产制造、电商等 Odoo 其他领域模块。

2. 业务全景分析

2.1 角色画像

角色说明权限

2.2 核心业务流程

流程 A：月度做账流（每月每客户，占工作量 70%）

收集资料（发票/银行回单/工资表）
  → 登记/导入进项发票、销项发票
  → 导入银行流水
  → 自动记账引擎批量生成凭证 → 人工补录调整凭证
  → 凭证审核过账（posted）
  → 期末结转损益（一键）
  → 出报表：资产负债表 / 利润表 / 科目余额表 / 总账 / 明细账

流程 B：申报流（每月/每季）

申报日历提醒（某客户某税种某属期 → 未申报）
  → 系统生成申报底稿（自动计算应纳税额，含计算过程）
  → 用户登录电子税务局人工申报（系统提供直达链接）
  → 回系统标记"已申报"，登记缴款金额与日期
  → 台账状态流转：未开始 → 待申报 → 已申报未缴款 → 已完成

流程 C：外贸客户流（部分客户）

出口业务发生 → 录入报关单（或从单一窗口导出数据后导入）
  → 开出口发票 → 收汇登记（币种/金额/汇率）
  → 结汇/待核查 → 出口退税资料归档 → 免抵退税台账

流程 D：收费流（代账公司自身收入）

客户合同（代账费标准/周期）→ 到期提醒 → 开票/收款登记 → 应收统计

3. Odoo 借鉴策略（本项目最重要的架构决策）

3.1 为什么不直接部署 Odoo 本体，而是"架构师从、实现自建"

对"以 Odoo 为基座"的两种路线做了评估：

维度路线 A：直接用 Odoo 社区版二次开发路线 B（本项目采用）：借鉴 Odoo 架构，轻量栈自建
运行环境必须 PostgreSQL + Python 3.11+ + 长驻多进程服务，本机还跑着 Ollama 大模型，内存吃紧Python + SQLite，单进程，常驻内存 < 200MB
部署/运维升级模块、数据库迁移、插件兼容问题，一人无 IT 运维扛不住双击 start.bat 即用，出问题删库重跑
中国本地化Odoo 社区版中国会计本地化（l10n_cn）能力薄弱，中国式凭证/申报台账仍要大量定制从第一天就按中国代账业务建模
许可证Odoo 社区版 LGPL-3.0：直接复制/修改其源码文件，修改部分须按 LGPL 开源（内部使用虽无碍，但定制模块发布受限）只借鉴其架构思想与数据模型设计（不受版权保护的思想层面），代码 100% 自研重写，不复制任何 Odoo 源码文件，无许可证包袱
功能匹配度Odoo 强项在电商/制造/库存/协同，对"一人管 100 家客户账"是 90% 冗余100% 按代账业务裁剪

决策：采用路线 B。 "以 Odoo 为基座"的含义 = 把 Odoo 最有价值的六大架构资产作为设计蓝本（见 3.2），而不是把它的代码跑起来。

3.2 从 Odoo 借鉴的六大架构资产

资产 1：模块化架构（Odoo addons 机制）

Odoo 中"一切皆模块"：每个模块是一个目录，含 models/（业务对象）、views/（界面定义）、security/（权限）、data/（初始化数据），由 __manifest__.py 声明依赖。模块可插拔、可叠加扩展。

→ 本项目实现：app/modules/<module_name>/ 目录约定，模块注册表机制（详见 5.3），每个模块自带 models、API 路由、视图配置（JSON）、种子数据，按依赖顺序自动加载。

资产 2：数据模型设计（Odoo account / contacts 模块的模型体系）

Odoo 的会计模型是业界教科书级的复式记账实现：

  • res.partner：统一的客户/供应商联系人模型（is_company、vat 税号等字段）
  • account.account：科目表（按公司隔离）
  • account.journal：账簿/日记账（sale/purchase/bank/cash/misc 五类）
  • account.move：凭证与发票统一模型（自 Odoo 13 起，发票、账单、手工凭证都是 account.move 的不同 move_type），状态机 draft → posted → cancel
  • account.move.line：凭证行（debit/credit/account_id/partner_id），借贷合计必须平衡（sum = 0）才能过账，且"已过账凭证不可修改"（只能红冲/冲销）
  • account.tax：税种定义（税率、税基类型）
  • res.company + company_id 字段：多公司机制——同一套表、每行数据带公司 ID、查询自动过滤

→ 本项目照搬这套模型设计并做中国化改造（凭证字、摘要、辅助核算、借贷方向红字冲销等），模型命名保持与 Odoo 一致的可对应关系（见第 6 章映射表）。

资产 3：模型驱动 UI（Odoo 视图 = XML 配置而非手写页面）

Odoo 的列表/表单/看板/日历/透视表视图是数据（XML）而非代码：开发者声明模型字段与视图配置，前端框架统一渲染。这使新增一个业务模块几乎不用写页面代码。

→ 本项目实现：视图配置 JSON（每模型声明 list/form 视图的字段、布局、筛选器、动作按钮），前端实现通用 ListView / FormView / KanbanView / CalendarView 渲染器消费这些配置。这是本项目的核心工程杠杆：通用视图组件写一次，所有模块复用。

资产 4：ORM 使用范式（Odoo models.Model）

Odoo ORM 的 recordset 风格：search(domain) 域过滤语法、create/write/unlink、计算字段（@api.depends）、约束校验（@api.constrains）、_order 默认排序、_rec_name 记录显示名。

→ 本项目实现：SQLAlchemy 2.0 declarative + 自研轻量基类 BaseModel（见 5.3.2），提供 domain 过滤解析、rec_name、审计字段（create_uid/create_date/write_uid/write_date，Odoo 同名字段）等约定。不重造完整 ORM，只吸收其约定。

资产 5：Chatter 与审计（Odoo mail.thread mixin）

Odoo 每条业务记录底部有"沟通区"（chatter）：显示操作日志（谁何时改了什么字段）与内部留言。

→ 本项目实现：通用 audit_log 表（model + record_id + 变更 JSON）+ 通用 note 表，FormView 底部统一渲染"活动日志"面板。

资产 6：自动化规则（Odoo automated actions / reconcile models）

Odoo 支持声明式自动动作（条件触发服务端动作）和银行对账规则模型（account.reconcile.model：按流水描述匹配 → 自动生成凭证）。

→ 本项目实现：自动记账规则表（触发条件 + 凭证模板，见 7.7），以及通用"计划任务"框架（备份、逾期提醒，见 7.13）。

4.2 选型理由（为什么不是别的）

  • 为什么不用 Odoo OWL 前端：OWL 是 Odoo 专用框架，社区小、文档少、Codex 训练数据覆盖差，产出质量风险高。Vue 3 与 OWL 设计理念一致（组件 + 响应式 + 虚拟 DOM），但生态成熟。
  • 为什么 SQLite 不是 PostgreSQL：数据量百万级（见 2.3）、单用户写入、无并发热点——SQLite WAL 完全胜任；换来的是"备份 = 复制一个文件"的极简运维，与 G5（云备份）直接对齐。
  • 为什么 FastAPI 不是 Flask/Django：Django 太重（admin/ORM/模板全套绑定）；Flask 能做但要手工拼的东西多。FastAPI + Pydantic + 自动文档，Codex 产出质量最稳。
  • 为什么不用服务端模板渲染（Jinja2 全栈）：本系统的交互复杂度（可编辑表格、拖拽看板、联动筛选）适合 SPA 模式；且"模型驱动 UI"需要前端持有视图配置动态渲染。

4.3 运行环境与部署

  • 目标机器：用户 Windows 本机（同时运行 Ollama 等），内存预算 < 300MB。
  • 启动方式：项目根目录 start.bat —— 检查 venv → 缺依赖则安装 → 启动 uvicorn（127.0.0.1:8000）→ 自动打开默认浏览器。
  • 配置文件：config.yaml（数据库路径、备份目录、端口、会话密钥），首次启动自动生成默认值并引导初始化管理员账号。
  • 数据目录：data/zhicai.db（SQLite 主库）+ data/attachments/（附件文件按 YYYY/MM/<uuid>.<ext> 组织，DB 只存元数据——与 Odoo 的 ir.attachment 文件存储策略一致）。

关键设计原则：

  1. 通用 API + 模型注册表（Odoo ir.model 思想）：每个 SQLAlchemy 模型在启动时注册到 ModelRegistry（表名、显示名、字段元数据、权限、默认视图配置）。FastAPI 动态生成 /api/v1/data/<model> 的 CRUD 路由；前端 ListView/FormView 通过 /api/v1/meta/<model> 拿到字段与视图配置后渲染。新增一个业务实体的开发成本 ≈ 定义一个 SQLAlchemy 模型 + 一份视图配置 JSON。
  2. 账套隔离中间件（Odoo 多公司 record rules 思想）：所有带 book_id 的模型，查询自动注入 book_id == 当前账套 过滤；显式声明"跨账套查询"才能绕过（仅仪表盘总览、客户列表等白名单场景）。
  3. 业务动作与 CRUD 分离：状态流转（过账、审核、对账、算税）一律走 /api/v1/biz/* 的显式动作端点，禁止前端直接改状态字段。

5.3.3 Domain 过滤语法（对标 Odoo search domain）

5.3.4 自动编号（对标 Odoo ir.sequence）

ir_sequence 表（code, prefix, padding, next_number, book_id）。凭证号规则：{凭证字}-{YYYYMM}-{0001}，按 账套+账簿+月份 重置计数；合同编号、任务编号同理。并发用 SQLite 单写者特性天然安全。

5.3.5 当前账套上下文（对标 Odoo 多公司切换）

  • 顶栏"账套切换器"：下拉列出全部启用客户（可搜索），选中写入会话 cookie。
  • 中间件解析 cookie → request.state.book_id；CRUD API 自动注入过滤（5.1 原则 2）。
  • "总览模式"（book_id=all）：仅 dashboard、res_partner 列表、tasks、tax_decl 日历等白名单模型可用，由模块在视图配置中显式声明 allow_cross_book: true。

对账工作台（7.8）从流水行发起"生成凭证"。

6.9 auto_entry 模块 —— 自动记账规则（对标 Odoo account.reconcile.model）

auto_entry_rule：

字段类型说明
namestr规则名，如"销项专票→确认收入"
triggerenuminvoice_output / invoice_input / bank_line / payroll

line_template 结构（支持变量替换）：

[
  {"side": "debit",  "account": "1122 应收账款",      "summary": "应收 {partner_name}", "amount": "{total_amount}"},
  {"side": "debit",  "account": "2221.01.02 进项税额", "summary": "进项税 {tax_amount}", "amount": "{tax_amount}"},
  {"side": "credit", "account": "6001 主营业务收入",   "summary": "销售 {goods_amount}", "amount": "{goods_amount}"}
]

占位符来源：源单据字段值（发票/流水/工资行）；{amount} 支持表达式（如 ={goods_amount}*0.13）。引擎必须保证生成凭证借贷平衡，不平衡则整单拒绝并写日志。

auto_entry_log：rule_id, source_model, source_id, result(ok/failed), move_id, message, created_at。

内置种子规则（可停用/修改）：

  1. 销项发票（任意类型）→ 借 应收账款{价税合计} / 贷 主营业务收入{不含税} + 贷 销项税额{税额}
  2. 进项发票按 category 映射 → 借 费用科目{不含税} + 借 进项税额{税额} / 贷 应付账款{价税合计}（category→科目映射表存 ir_config，可维护）
  3. 银行流水"摘要含'工资'且贷方支出" → 借 应付职工薪酬 / 贷 银行存款
  4. 银行流水"摘要含'税'且贷方支出" → 借 应交税费-未交增值税 / 贷 银行存款
  5. 银行流水"借方收入" → 借 银行存款 / 贷 应收账款（配合核销）
  6. 工资批次审核后 → 计提与发放两张凭证模板

6.10 tax_decl 模块 —— 申报台账

tax_calendar_rule（征期规则）：id, tax_kind(enum: vat/cit quarterly/cit annual/iit/surtax/stamp/…), period_type(enum: monthly/quarterly/yearly), deadline_rule(str, 如 "next_month_15" / "quarter_next_month_15" / "annual_0531"), applies_to(JSON 过滤：{"taxpayer_type":"small"}), enabled。

种子规则：

  • vat：小规模→季度，次季首月 15 日截止；一般纳税人→月度，次月 15 日
  • cit 季度预缴：次季首月 15 日；cit 年度汇算：次年 5 月 31 日
  • iit（个税）：次月 15 日
  • 印花税：按季（季首 15 日）——按用户实际业务，税目仅买卖合同 0.3‰
  • 附加税（城建 7%/5%/1%、教育附加 3%、地方附加 2%）：随增值税

生成逻辑：计划任务每月 1 日（及季度/年度节点）扫描全部启用账套 × 适用征期规则 → 批量生成当期 tax_decl_item；已存在的跳过（幂等）。

7. 功能模块规格（界面行为与验收口径）

本章按模块给出功能点、交互与验收标准（DoD）。通用规则：所有列表视图支持筛选/排序/分页/导出 CSV；所有表单有必填校验与脏数据离开提示；所有删除为归档（active=False）。

7.1 登录与全局框架（AppShell）

  • 首次运行向导：创建 admin 账号 → 设置数据目录与 OneDrive 备份目录 → 完成进入。
  • 登录页：账号 + 密码；登录后进入工作台。
  • 左侧导航栏（借鉴 Odoo 应用菜单，可折叠）：分组显示模块菜单（工作台 / 客户与合同 / 记账 / 发票与银行 / 税务申报 / 外贸专区 / 工资 / 任务与文档 / 系统）。菜单项由模块注册表驱动——装了什么模块就显示什么（Odoo 同款机制）。外贸专区仅当至少一个账套 is_foreign_trade=true 时显示。
  • 顶栏：左侧当前页面标题面包屑；中部全局搜索（输入客户简称/凭证号/发票号，返回分类结果跳转）；右侧账套切换器（下拉搜索 100 家客户）+ 用户菜单（修改密码/退出）。
  • 账套切换后：左侧模块不变，主区域数据全部切换到该账套；总览模式下仪表盘等白名单页面跨账套聚合。
  • DoD：登录/登出/会话过期拦截（跳登录页）；账套切换 1 秒内完成；全局搜索回车直达。

7.2 首页工作台（Dashboard，借鉴 Odoo board）

仪表盘卡片（可配置显示与顺序）：

卡片内容
本月概览服务客户数（active 账套数）、本月待过账凭证数、本月已过账凭证数、本月新发票数
申报日历红牌未来 7 天到期且 state∈{pending,preparing} 的申报项列表（客户×税种×截止日），点击直达
逾期预警已逾期未申报、逾期未收代账费（contract_fee_item overdue）
待办任务state∈{todo,doing} 的任务前 10 条
收款月历本月应收代账费合计/已收/未收
各客户进度表格：客户 × 本月（收票/凭证/申报/收费）四状态灯 —— 一屏看清 100 家谁没做完
  • DoD：仪表盘总览模式跨账套聚合正确；每张卡片可点击穿透到对应列表页。

7.3 客户管理（res_book + res_partner）

  • 客户列表（总览模式）：编号/简称/税号/纳税人类型/服务状态/外贸标记/合同到期日；支持按纳税人类型、状态筛选；行点击进入该客户详情页（自动切换账套上下文）。
  • 客户详情页（FormView 标签页）：基本信息 / 科目表 / 账簿 / 申报设置 / 合同收费 / 往来单位 / 文档 / 活动日志。
  • 新建客户向导：填基本信息 → 选会计准则 → 一键初始化（克隆科目模板 + 建账簿 + 建征期规则 + 生成当年台账）。
  • 停用客户：charge_status→terminated 后从切换器隐藏，数据保留。
  • DoD：新建客户后科目表完整（小企业准则一级+预置二级科目齐全，科目树可展开）；重复税号拦截；100 家客户时列表加载 < 500ms。

7.4 合同与收费管理（contract）

  • 合同列表+表单：基本要素、服务范围多选、收费周期与金额；到期前 30 天自动生成"续约提醒任务"。
  • 收费计划：按合同周期自动生成各期 contract_fee_item（幂等，可手动补）；状态流转 unpaid→invoiced→paid；逾期自动标 overdue 并生成催收任务。
  • 收款登记：批量勾选多客户多期一起标记收款（一键场景：月末统一收 60 家）。
  • 报表：应收统计（按客户/按月份）；本年度已收合计。
  • DoD：自动生成收费计划不重复不遗漏；逾期判定（today > due_date 且 unpaid）正确。

7.5 记账核心（account）—— 最重模块

凭证列表：默认按期间倒序；筛选（期间/凭证字/状态/来源/摘要关键词/科目）；批量操作（批量过账/批量打印）。行内快览（点开展开分录，不进详情页）。

凭证录入页（定制页面，不用通用 FormView）：

  • 表头：凭证字（下拉）、日期、附件数；
  • 分录表格（类 Excel 连续录入）：摘要（支持上一行摘要按 // 复制）、科目（编码/名称拼音联想，仅末级）、辅助核算（往来单位等按科目配置动态出现）、借方/贷方金额（输入一侧自动清另一侧）；回车自动加行；
  • 底栏实时显示"借方合计 / 贷方合计 / 差额"，不平衡时【保存】可用但【保存并过账】禁用（红色差额提示）；
  • 常用凭证模板：任意凭证可存为模板，模板一键带出分录（含科目不含金额）。

过账/红冲：过账动作执行 6.5 全部约束校验；红冲生成反向凭证（每行借贷互换、摘要前加"红冲："），两张凭证互链且原凭证 state→voided。

期末结转（一键）：选择期间 → 系统将损益类科目（6001/6051/6111/6301/6401/6402/6403/6601/6602/6603/6711/6801）余额结转到 3103 本年利润，生成结转凭证（source_type=closing）；重复执行同期间提示已结转。结账（period close）后期间锁定。

账簿查询：

  • 总账：科目×期间的汇总（期初/本期借/本期贷/期末）；
  • 明细账：科目下按凭证展开（日期/凭证号/摘要/借/贷/方向余额）；
  • 科目余额表：全科目期初/发生/期末，支持期间区间，导出 Excel/CSV；
  • 凭证连打：按期间连续打印凭证（打印样式：标准记账凭证版式，A4 两张/页）。

财务报表：资产负债表、利润表（小企业准则格式，公式取数映射存 ir_config，允许用户微调公式）；报表数字与账联查（点数字弹出构成明细）。

  • DoD：① 每张凭证过账校验全通过（单测覆盖每个约束分支）；② 结转后损益科目余额为 0、本年利润正确；③ 资产负债表"资产=负债+权益"平衡校验内置（不平则报表顶部红条警示并显示差额）；④ 利润表净利润 = 本年利润科目发生额。

7.6 发票管理（invoice）

  • 进项/销项两个列表页（Tab 切换）；表单录入（自动算价税合计）；发票影像上传（拍照/扫描件，进 doc_documents）。
  • Excel 批量导入：模板下载 → 导入 → 预览校验（错误行标红说明）→ 确认入库；查重（同账套代码+号码+日期）。
  • 月末视图：某期间进项合计/销项合计/税额合计（申报底稿取数来源）。
  • DoD：导入 500 行 < 5 秒；重复发票拦截；价税合计自动计算精度正确（Decimal）。

7.7 自动记账引擎（auto_entry）—— 核心卖点

  • 规则管理页：规则列表（启停/优先级/编辑）。
  • 批量执行工作台：选账套+期间 → 列出所有未生成凭证的发票/流水 → 逐条匹配规则（显示"将执行的规则+预览分录"）→ 勾选执行 → 批量生成 draft 凭证 + 执行日志。匹配不到规则的留在"待人工"清单。
  • 幂等：已 entry_generated 的发票不再生成；失败整单回滚并记 auto_entry_log。
  • DoD：种子规则全链路测试——给定 3 张销项票+2 张进项票+3 条流水，批量执行后生成 8 张平衡 draft 凭证且金额科目全部正确；同批重复执行不重复生成。

7.8 银行对账工作台（bank）

  • 流水导入（Excel/CSV：银行导出格式适配常见工行/建行/招行模板，字段映射可配置存 ir_config）。
  • 对账工作台：左右分栏——左：流水列表（未对账优先）；右：选中流水的凭证预生成区（命中规则自动带出，可改科目）；一键"生成凭证并标记已对账"。
  • 按月对账汇总：期初余额 + 收入 - 支出 = 期末余额（与银行对账单核对）。
  • DoD：导入含表头乱码（GBK/UTF-8 自动识别）容错；生成凭证后流水状态联动。

7.9 税务申报台账与日历（tax_decl）—— 防"漏报"的核心

  • 申报日历页（总览模式）：月历视图 + 列表视图切换。列表按月份展示：客户 × 税种 × 属期 × 截止日 × 状态（颜色：pending 灰 / preparing 蓝 / submitted 橙 / paid 绿 / exempt 白 / 逾期红）。
  • 台账行操作：①"计算"——打开申报底稿抽屉：显示系统计算的应纳税额与计算过程快照（例：增值税=销项合计-进项合计+上期留抵，取数自发票与台账，过程可追溯）；②"标记已申报"（填实缴额）；③"标记已缴款"（填缴款日期）；④"免税/零申报"（记录原因）。
  • 官网直达：每税种提供电子税务局/自然人电子税务局等外链按钮（链接存 ir_config，用户可维护）——系统不做自动申报，只做导航与登记。
  • 增值税计算底稿（M4 范围）：一般纳税人=当期销项-当期进项-上期留抵；小规模=含税收入/1.03×3%（季度 30 万免征判断可配置，默认按现行政策参数存 ir_config）。附加税=实缴增值税×税率。印花税=买卖合同计税依据×0.3‰（计税依据默认取当期购销合计，可手改）。企业所得税、个税底稿仅出取数汇总（营业收入/成本/利润总额），计算以用户在税局端为准。
  • DoD：征期规则批量生成台账幂等且覆盖 100 账套 < 10 秒；逾期自动标红；每笔计算底稿可追溯取数来源（数字穿透到发票/凭证列表）。

7.10 外贸专区（foreign_trade，仅外贸账套可见）

  • 报关单台账：列表+表单（含商品行子表）；单一窗口导出的报关明细 CSV 导入。
  • 收汇台账：登记收汇/结汇，关联报关单（一笔报关多次收汇）。
  • 出口退税台账：状态流转收集→申报→审批→到账。
  • 平台链接中心：单一窗口 / 电子口岸 / 国家外汇管理局数字外管 / 电子税务局出口退税模块的直达链接 + 用户可编辑的操作备忘（文本）。
  • DoD：非外贸账套看不到外贸菜单；报关单-收汇关联正确显示未收汇差额。

7.11 工资社保（payroll）

  • 按月建批次：复制上月员工行（金额可改）→ 计算个税（累计预扣法，税率表可配置）→ 确认 → 一键生成两张凭证（计提：借 管理费用-工资 / 贷 应付职工薪酬；发放：借 应付职工薪酬 / 贷 银行存款，个税代扣进 应交税费-应交个人所得税）。
  • 社保公积金台账：基数、单位/个人部分，随批次登记。
  • DoD：个税计算单测（3 档税率边界值）；批次确认后凭证自动生成且平衡。

7.12 文档中心（documents）

  • 全局文档列表（跨账套）：按客户/类型/标签/年份筛选；拖拽上传（多文件）；图片/PDF 在线预览。
  • 业务单据挂接：发票、凭证、报关单表单内直接上传附件（自动登记到文档中心并双向关联）。
  • DoD：上传 10MB PDF 正常；从发票页上传后文档中心可反查来源单据。

7.13 数据备份与计划任务（core/scheduler + base 设置页）

  • 自动备份：每日首次启动系统时 + 每日固定时刻（可配）执行：PRAGMA integrity_check → 备份 SQLite（VACUUM INTO）到 OneDrive 目录 zhicai_backup/zhicai_YYYYMMDD_HHMM.db → 保留最近 90 份自动清理 → 写备份日志（时间/大小/结果）。
  • 手动"立即备份"按钮（系统设置页）+ 备份历史列表 + "从备份恢复"引导（说明文档式，不自动执行覆盖）。
  • 计划任务框架（对标 Odoo ir.cron）：任务注册（backup / decl_generate 台账生成 / fee_overdue 逾期扫描 / task_reminder 到期提醒），每日 00:05 服务器启动后补跑错过的任务；执行留痕。
  • DoD：备份文件可用（恢复到临时库校验通过）；90 份滚动清理正确；日志可查。

  • 审计日志查看（按用户/模型/时间筛选）；
  • 数据维护：数据库健康检查、备份入口、科目模板管理、导出全量数据（CSV 包）。

11. Codex 开发指引

11.1 工程规范

  • Python：类型标注全覆盖；service 层抛业务异常（自定义 BizError(code, message)），API 层统一转 HTTP 400/409；禁止在路由层写业务逻辑。
  • 前端：ES Modules，无构建；组件文件 = 单文件 Vue 组件（Vue.defineComponent + 模板字符串）；通用渲染器与业务定制页分离（components/ vs modules/）。
  • Git：里程碑一次或多次提交均可，提交信息格式 M2: 凭证录入页与过账校验。
  • 时间处理：业务日期一律 naive date（字符串 YYYY-MM-DD 出入参）；金额 Decimal，JSON 序列化为字符串。
  • 错误信息面向用户可读（中文），日志面向开发者（含堆栈）。
